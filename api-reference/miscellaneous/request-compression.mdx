## Overview

NanoGPT accepts compressed JSON request bodies on text-generation endpoints. Compression is useful for requests with long conversation histories, large tool schemas, or other repeated text. These payloads often become 4–6× smaller, which can improve time to first token when upload bandwidth or network latency is the bottleneck.

Request compression does not change the API response format. Streaming and non-streaming responses work as usual.

## Supported Endpoints

| Endpoint | API format |
| --- | --- |
| `POST /v1/chat/completions` | OpenAI Chat Completions |
| `POST /api/v1/chat/completions` | OpenAI Chat Completions alias |
| `POST /v1/responses` | OpenAI Responses |
| `POST /v1/messages` | Anthropic Messages |

Other endpoints, including embeddings and media generation, do not currently accept compressed request bodies.

## Supported Encodings

Compress the JSON body and set one `Content-Encoding` header:

| `Content-Encoding` | Format |
| --- | --- |
| `gzip` | Gzip; recommended default |
| `x-gzip` | Legacy alias for gzip |
| `deflate` | Zlib-wrapped or raw DEFLATE |
| `br` | Brotli |
| `identity` | Body is not compressed |

Use `Content-Type: application/json` for the decompressed content. Do not send more than one encoding.

## Examples

The examples below use gzip because it is widely available.

<CodeGroup>

```bash cURL
printf '%s' '{"model":"openai/gpt-5.2","messages":[{"role":"user","content":"Hello"}]}' \
  | gzip -c \
  | curl https://nano-gpt.com/v1/chat/completions \
      --request POST \
      --header "Authorization: Bearer $NANOGPT_API_KEY" \
      --header "Content-Type: application/json" \
      --header "Content-Encoding: gzip" \
      --data-binary @-
```

```python Python (requests)
import gzip
import json
import os

import requests

payload = {
    "model": "openai/gpt-5.2",
    "messages": [{"role": "user", "content": "Hello"}],
}

body = gzip.compress(json.dumps(payload).encode("utf-8"))
response = requests.post(
    "https://nano-gpt.com/v1/chat/completions",
    data=body,
    headers={
        "Authorization": f"Bearer {os.environ['NANOGPT_API_KEY']}",
        "Content-Type": "application/json",
        "Content-Encoding": "gzip",
    },
)

response.raise_for_status()
print(response.json())
```

```javascript Node.js
import { gzipSync } from "node:zlib";

const payload = {
  model: "openai/gpt-5.2",
  messages: [{ role: "user", content: "Hello" }],
};

const response = await fetch("https://nano-gpt.com/v1/chat/completions", {
  method: "POST",
  headers: {
    Authorization: `Bearer ${process.env.NANOGPT_API_KEY}`,
    "Content-Type": "application/json",
    "Content-Encoding": "gzip",
  },
  body: gzipSync(JSON.stringify(payload)),
});

if (!response.ok) {
  throw new Error(`Request failed: ${response.status} ${await response.text()}`);
}

console.log(await response.json());
```

</CodeGroup>

When using Python Requests, pass the compressed bytes with `data=body`. Using `json=payload` sends an uncompressed JSON body instead.

## Rules and Limits

- **Size limits use the decompressed body.** The decompressed JSON must be no larger than the standard 32 MiB text-request limit. The compressed input is also limited to 32 MiB. If either limit is exceeded, the API returns `413 Payload Too Large`.
- **Only one encoding is allowed.** Stacked or comma-separated values such as `Content-Encoding: gzip, br` return `415 Unsupported Media Type` with error code `unsupported_content_encoding`.
- **Unknown encodings are rejected.** Any `Content-Encoding` value not listed above returns the same `415` error.
- **The body must contain valid compressed JSON.** Malformed compressed data returns the same `400` invalid-JSON error as malformed uncompressed input.
- **Authentication happens first.** A valid API key is required before NanoGPT decompresses the body. Unauthenticated compressed requests are rejected without being decompressed.
- **Responses are unchanged.** Compression applies only to the request body; response parsing and SSE streaming behavior remain the same.

Requests without `Content-Encoding` continue to behave as uncompressed JSON requests.

## When to Compress

Compression has a small CPU cost. As a practical starting point, compress request bodies larger than about 10 KB and leave smaller requests uncompressed. Benchmark with your own payloads and client locations if latency is important.

Use gzip unless you have a specific reason to choose another encoding. Brotli usually produces slightly smaller payloads, while gzip has broader runtime and tooling support.

## FAQ

### Do I need to change how I read responses?

No. This feature only changes how the request body is uploaded.

### Can I use compression with streaming?

Yes. Set `stream: true` in the decompressed JSON as usual. Request compression does not change the [streaming protocol](/api-reference/miscellaneous/streaming-protocol).

### Does this work with embeddings or media endpoints?

No. Request compression currently applies only to the text-generation endpoints listed above.
