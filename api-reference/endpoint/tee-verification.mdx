## Overview

This guide covers TEE models served through RedPill. Each request requires a verified upstream: if none is available, the request fails with a `503` instead of being served. Other TEE routes, such as Tinfoil and Chutes TEE, don't have these receipts.

RedPill signs a receipt for each response. A receipt records what its gateway received, which upstream it verified and what it returned, with a hash of each body, and is signed with a key from the gateway's attestation report.

Confidentiality and logging outcomes are provider-specific, and plaintext may still exist at gateway or proxy layers outside the enclave.

## Response headers

| Header | Meaning |
| --- | --- |
| `X-TEE-Signature-Available` | `true` when the response has a signed receipt. |
| `X-Receipt-Id` | The receipt ID (`rcpt-...`). |
| `X-TEE-Signature-ID` | The same receipt ID. |
| `X-TEE-Completion-ID` | Non-streaming only. The response body `id`, which also finds the receipt. |
| `X-Aci-Version`, `X-Aci-Keyset-Digest` | The receipt format version and the digest of the gateway's signing keys. |

Receipts are available on Chat Completions. Non-streaming Responses API replies don't include one, and the Messages API and streaming Responses API reject these models.

## What a receipt can prove

| Check | Streaming | Non-streaming | Non-streaming in exact mode |
| --- | --- | --- | --- |
| The receipt was signed by a key in the attestation report | Yes | Yes | Yes |
| The upstream was verified | Yes | Yes | Yes |
| `response.returned` matches the bytes you received | Yes | No | Yes |
| `request.received` matches the bytes you sent | No | No | No |

NanoGPT adapts each request before forwarding it, so `request.received` covers the request NanoGPT sent.

The response checks don't hold for `TEE/gemma-4-31b-it` and `TEE/deepseek-v3.2`, whose replies NanoGPT always rewrites, and exact mode isn't available for them.

## Exact mode for non-streaming replies

NanoGPT normally rebuilds non-streaming replies, so their bytes differ from what the receipt covers. To get the bytes the receipt covers, send this header on `/v1/chat/completions`:

```bash
curl -D headers.txt -o body.json "https://nano-gpt.com/api/v1/chat/completions" \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/json" \
  -H "X-NanoGPT-TEE-Response: exact" \
  -d '{"model":"TEE/glm-5.3-flash","messages":[{"role":"user","content":"Hello"}]}'

shasum -a 256 body.json
```

Check that the response has `X-NanoGPT-TEE-Response: exact`, which only exact replies return. Then compare the hash with `response.returned.body_hash` in the receipt named by `X-Receipt-Id`. If `X-TEE-Signature-Available` is `false`, there's no receipt to compare it with.

The body is what RedPill returned, unchanged, even if it's empty or malformed. This means:

- There's no `x_nanogpt_pricing`. Read the cost from `GET /api/v1/usage/requests/{X-Request-ID}`, which can return a `404` for a few seconds after the reply.
- `model` is the upstream model ID. `X-Requested-Model` holds the one you sent.
- NanoGPT doesn't repair tool calls, filter reasoning or retry empty replies.
- NanoGPT doesn't try another provider. If RedPill can't serve the request, you get an error.

No bytes arrive until the whole reply is finished, so allow a long client timeout. `nano-gpt.com` closes a connection that has received no bytes after about 5 and a half minutes, so use streaming for replies that may take longer.

On Chat Completions, exact mode returns a `400` with code `tee_exact_response_unsupported` for models it doesn't cover, requests that would use your own provider keys, Context Memory, web search, `reasoning.exclude`, PII redaction and more than one choice.

The header has no effect on streaming requests, whose replies already match, on x402 payments or on the Responses, Messages and text completions endpoints. Those replies don't include the `X-NanoGPT-TEE-Response` header.

## Fetch a receipt

Use the `X-Receipt-Id` value or the response body `id`, with the API key of the account that made the request. For streams, fetch it after the stream ends, because the receipt covers the whole stream. A stream that's cut off can't be verified: it usually has no receipt, even if its headers named one, and any receipt it does have won't match the bytes you received.

```bash
curl "https://nano-gpt.com/api/v1/tee/signature/{receiptId}?model=TEE/glm-5.3-flash" \
  -H "Authorization: Bearer $API_KEY"
```

The response contains:

- `receipt`: the signed receipt. Its `event_log` holds the `request.received`, `response.returned` and `upstream.verified` events, and `signature` is signed over the rest of the receipt.
- `text`, `signature`, `signing_address`, `signing_algo`: an older ECDSA signature over `<request hash>:<response hash>`.

NanoGPT allows lookups for 7 days after the request, as long as RedPill still holds the receipt. `X-Request-ID` values aren't accepted.

If a chat response has an `X-TEE-Verification-Route` header, also send that header on this request and on the attestation request below. Its value expires after one hour.

## Fetch the attestation report

Send a fresh nonce of 64 lowercase hex characters.

```bash
curl "https://nano-gpt.com/api/v1/tee/attestation?model=TEE/glm-5.3-flash&nonce=$(openssl rand -hex 32)" \
  -H "Authorization: Bearer $API_KEY"
```

The report attests the gateway. `attestation.workload_keyset` holds its signing keys and `attestation.evidence.quote` its TDX quote. Evidence for the upstream is in the session the receipt names in `upstream.verified.session_id`, at `https://api.redpill.ai/v1/aci/sessions/{session_id}`.

Don't pin `workload_keyset_digest`: it changes when the gateway renews its keys.

## Python example

```bash
pip install requests cryptography
NANOGPT_API_KEY=YOUR_API_KEY python3 test_tee.py
```

```python
#!/usr/bin/env python3
"""Check a NanoGPT TEE response against its signed receipt."""
import hashlib
import json
import os
import secrets
import time

import requests
from cryptography.hazmat.primitives.asymmetric.ed25519 import Ed25519PublicKey

BASE_URL = "https://nano-gpt.com/api"
MODEL = "TEE/glm-5.3-flash"
HEADERS = {"Authorization": f"Bearer {os.environ['NANOGPT_API_KEY']}"}


def digest(data: bytes) -> str:
    return "sha256:" + hashlib.sha256(data).hexdigest()


def canonical(value) -> bytes:
    # JSON Canonicalization Scheme (RFC 8785), which is this simple here
    # because these documents hold only ASCII keys, strings and integers.
    return json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False).encode()


def stream_completion() -> tuple[str, bytes]:
    response = requests.post(
        f"{BASE_URL}/v1/chat/completions",
        headers=HEADERS,
        json={
            "model": MODEL,
            "stream": True,
            "messages": [{"role": "user", "content": "Reply with the single word: ok"}],
        },
        stream=True,
        timeout=120,
    )
    response.raise_for_status()
    receipt_id = response.headers["X-Receipt-Id"]
    # The receipt covers the exact bytes of the stream, so don't reassemble them.
    return receipt_id, b"".join(response.iter_content(chunk_size=None))


def fetch_receipt(receipt_id: str) -> dict:
    # A stream's receipt is complete shortly after the stream ends.
    for _ in range(10):
        response = requests.get(
            f"{BASE_URL}/v1/tee/signature/{receipt_id}",
            headers=HEADERS,
            params={"model": MODEL},
            timeout=30,
        )
        if response.status_code == 200:
            return response.json()["receipt"]
        if response.status_code not in (404, 502, 503):
            response.raise_for_status()
        time.sleep(2)
    raise RuntimeError(f"Receipt {receipt_id} not available: {response.text}")


def fetch_workload_keyset(expected_digest: str) -> dict:
    report = requests.get(
        f"{BASE_URL}/v1/tee/attestation",
        headers=HEADERS,
        params={"model": MODEL, "nonce": secrets.token_hex(32)},
        timeout=30,
    )
    report.raise_for_status()
    keyset = report.json()["attestation"]["workload_keyset"]
    if digest(canonical(keyset)) != expected_digest:
        raise RuntimeError("The attested keyset does not match the receipt's workload_keyset_digest")
    return keyset


def verify_signature(receipt: dict, keyset: dict) -> None:
    unsigned = {key: value for key, value in receipt.items() if key != "signature"}
    key = next(k for k in keyset["receipt_signing_keys"] if k["key_id"] == receipt["key_id"])
    public_key = Ed25519PublicKey.from_public_bytes(bytes.fromhex(key["public_key"].removeprefix("0x")))
    # Raises InvalidSignature when the receipt was not signed by the attested key.
    public_key.verify(bytes.fromhex(receipt["signature"].removeprefix("0x")), canonical(unsigned))


def main() -> None:
    receipt_id, body = stream_completion()
    receipt = fetch_receipt(receipt_id)
    events = {event["type"]: event for event in receipt["event_log"]}

    keyset = fetch_workload_keyset(receipt["workload_keyset_digest"])
    verify_signature(receipt, keyset)
    print("Receipt signature verified against the attested keyset")

    if events["response.returned"]["body_hash"] != digest(body):
        raise RuntimeError("The receipt does not cover the bytes this client received")
    print("Response bytes match the receipt")

    upstream = events["upstream.verified"]
    if upstream["result"] != "verified" or upstream["required"] is not True:
        raise RuntimeError(f"The upstream was not verified: {upstream}")
    print(f"Upstream verified, session {upstream['session_id']}")


if __name__ == "__main__":
    main()
```

## What this example doesn't check

The example trusts the attestation report it fetches. For a full check, also verify the TDX quote and its nonce binding, the release measurements and the upstream session evidence. See [RedPill's verification guide](https://docs.redpill.ai/guides/verify-a-response).
